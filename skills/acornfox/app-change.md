# 改一个已装的应用：升级、退回、改设置、删了重装

**什么时候读这一册**：用户问“这个应用有没有新版本”“帮我升级 X”“升完出问题了，退回去”；要改一个从应用中心装的应用的设置（模型名、标题、端口、时区）、让它跟上平台变了的值（`APP-VARS-01`）；问“这个应用的密码、地址、时区是怎么设的”；要把应用删了再接上旧数据装回来、换版本。看状态、日志、启停、备份读 `app-life.md`；第一次装应用读 `app-center.md`。

## 升级应用中心里的应用、出问题退回

什么时候用：用户问“这个应用有没有新版本”“帮我升级 X”“升完出问题了，退回去”，或 `doctor`、`acornfox status 应用名` 里说“有新版本”时。**平台从不自己升级，一定要用户点头。** 升级 = 先把应用的数据存一份快照在本机（打包时应用会暂停一阵，自动另存的至少留 7 天、每种最新 3 份也留着），再换上目录里的新版本、重启、健康检查；任何一步没成功都**自动退回**到升级前（用快照恢复，数据和设置都是升级前的）。升级成功后快照还留着，出问题可以手动退回（会丢升级后写进应用的新数据）。更早的版本没有这些命令（报用法错误，退出码 2），这时只能走下一节的“删了重装”，并告诉用户要 v0.7.0 起。

**最低路径（照着做）：**

1. 看哪些有新版本：`acornfox --json apps outdated`（它会先看距上次成功同步是否超过 30 分钟，超过就先同步一次目录，最多等 60 秒；输出里 `catalog_sync.ok` 是 false 就是这次没同步成功，按上次同步到的目录算，原话转述给用户即可，不要连着重试；目录平时每 6 小时自动同步一次，用户打开控制台的应用中心或“我的应用”时也会看一眼，所以新上架的版本一般不会等很久）。`count` 是 0：告诉用户都是最新的，到此为止。`apps[]` 里 `available` 是新版本、`current` 是现在的；`blocked` 不是空的就是现在升不了，原话转述（`blocked_code` 是 `CAT-INST-08` 的说“要先升级 AcornFox”，升级 AcornFox 照 `maintain.md` 的“升级、卸载”一节，先问用户）；`snapshot`、`can_rollback` 说这个应用有没有升级前的快照可退。
2. **先看计划（只读）**：`acornfox --json apps upgrade 应用名 --plan`。看 `plan`：
   - `can_upgrade` 是 `false`：`blocked` 说了为什么，`blocked_code` 是编号，不要再往下做：`APP-UPG-02`（新版本要用户先补东西：多了一项必填设置，或要的内存比现在多）——问用户要值，升级时加 `--set 设置名=值`（保密的值写成 `设置名=-`，从标准输入给一行，不要写在命令里），内存不够问用户同意后 `acornfox app set --app 应用名 --memory 数字`；`APP-UPG-03`（新版本多了数据目录、提供的服务变了、多需要一个必须的服务）——这个版本现在升不了，应用照常用，告诉用户，要用新版本只能保留数据删掉重装（下一节，先问用户）；`BKP-01`（磁盘不够留快照）——把数字告诉用户，清理磁盘由用户定；`APP-UPG-01`——已经最新、停着、正在装或升级等，照 `message`。
   - `can_upgrade` 是 `true`：`summary` 是要对用户说的话；`vars_added`、`vars_removed`（新增、去掉的设置）、`uses_changed`、`notes`、`snapshot_mb`（快照约多大）一并说清。
3. 一句话说清：“把 X 从 <from> 升到 <to>：先把数据存一份快照（约 <snapshot_mb> MB），应用会暂停一阵再重启，大概几分钟用不了；没成功会自动退回。”用户这次的话本身就是要升（“帮我升到最新”“把 X 升级”），而且计划里没有他不知道的后果（`vars_added` 里没有**必须他填、没有默认值**的设置——有默认值的新设置照默认装，做完告诉他多了哪一项、值是什么；没有 `uses_changed` 要接新服务；`notes` 里没有丢数据的提醒），这一句就是计划要点，当已同意，直接做。用户只是问“有没有新版本”，或者计划里有上面这些后果，就在这句后面问一句“现在升吗？”，用户明确说要才继续。**用户没有说要升的时候，不要自己加 `--yes`。**
4. `acornfox --json apps upgrade 应用名 --yes`（要给新设置值的加 `--set`）。命令会等它做完（默认最多 10 分钟，数据大加 `--timeout 1800`，或 `--no-wait` 再用 `acornfox --json install status 任务编号 --wait` 等，直到 `done` 是 `true`，没到之前什么结论都不下）。`ok` 是 `true`、`say` 说“已升级”才算好。
5. 做完用 `acornfox --json status 应用名` 和 `acornfox --json apps vars 应用名` 核对：版本是新的，设置在；再照 `app-life.md` 的“确认应用能打开”确认它真的能打开。告诉用户升好了，升级前的快照（`apps[].snapshot_id`，种类 `pre-upgrade`）还留着：自动另存的至少留 7 天、每种最新 3 份也留着，出问题可以退回，但退回会丢升级后写进应用的新数据。任务 `apps[].affected_apps` 不是空的：这些应用的设置落在后面了，按“改一个应用的设置、让它跟上”一节问用户要不要让它们跟上。
6. 失败时看 `fault.code`：`APP-UPG-05`——已经自动退回到升级前，应用照旧在运行，数据和设置都是升级前的；把 `message` 里的原因告诉用户（原因里的编号用 `acornfox faults 编号` 看），处理好原因再升，**不要连着重试**。`APP-UPG-06`——退回也出了错，**停下**，把原话和 `acornfox backup list 应用名` 的输出交给用户，不要再升、不要删东西。

**升级后出问题，退回到升级前（会丢数据，必须先问用户）：**

1. `acornfox --json apps rollback 应用名 --plan`：`can_rollback` 是 `false`：`blocked` 原话转述（没有升级前的快照、快照就是现在的版本、快照坏了或那个版本的程序已经不在这台机器上，`APP-UPG-07`），到此为止。
2. **停下问用户**（退回会丢数据，用户说“退回去”也要问）：“退回会把 X 换成 <to> 版本升级前（<snapshot_at>）的数据和设置：升级之后写进应用的新数据会没有（退回前我会先把现在的数据另存一份，需要时能找回）；应用会重启一次。要退回吗？”
3. 用户明确同意后 `acornfox --json apps rollback 应用名 --yes`，等到 `done`。成功后告诉用户退回到哪个版本、`apps[].notes` 里写的另存备份是哪份：**退回前另存的就是升级后的新数据**，种类是 `pre-restore`（恢复前），存在这台服务器的备份目录里（`acornfox --json backup list 应用名` 看得到），**至少留 7 天、每种最新 3 份也留着**，不会被后来的恢复、备份挤掉；超过 7 天又不在最新 3 份里才会被清，磁盘放不下新备份时也可能被提前清（计划里会写明）。想找回升级后的新数据就趁早恢复它，照 `app-life.md` 的“备份和恢复应用数据”一节，先问用户；做好以后照 `app-life.md` 的“确认应用能打开”确认。目录里的新版本之后会重新提醒。失败：`APP-UPG-09`——应用保持退回前的样子，转述原因；`APP-UPG-10`——**停下**，交给用户。

**可以发挥的地方：** 解释新版本改了什么（`plan` 里的设置变化）；建议重要数据先 `backup create` 再升；建议升级放在没人用的时候；告诉用户快照占多大、占的是备份目录的磁盘（`acornfox backup list`）。

**必须先问用户的：** 升级本身（会重启）、退回（会丢升级后的新数据）、补设置的值、调内存、保留数据删掉重装、清理磁盘。

## 改一个应用的设置、让它跟上

什么时候用：① 用户要改一个从应用中心装的应用的设置（模型名、标题、端口这类；平台自动填的时区、下载源也行，只改这一个应用）；② 平台上的值变了（换了时区、下载源，设了平台域名）、接的服务变了（提供方换了地址、密码），或者对外方式、域名改了，应用里用的还是旧的（`apps vars` 里 `APP-VARS-01`，`doctor` 也会报）。它会重新算这个应用的环境变量、启动命令和配置文件，**重启这个应用**（数据不动），健康检查通过后做清单里写好的步骤；失败自动退回原来的样子。更早的版本没有这些命令（报用法错误，退出码 2），告诉用户要 v0.7.0 起。

**最低路径（照着做）：**

1. 想清楚改什么。`acornfox --json apps vars 应用名`：`can_change` 是 `false` 的（清单没存、旧格式）不能改，照实说，到此为止；每一行 `can_edit` 是 `true` 的才能用 `apps set` 改，`edit_how` 就是命令，**照它抄**：`apps vars` 里应用自己的参数显示成 `params.title`，命令里写 `title=值`（去掉 `params.`）；平台变量显示成 `platform.tz`，命令里写 `platform.tz=值`（带着前缀）；不要把 `params.` 写进命令。`false` 的不要试（`editable` 是 `never` 的改了应用会坏；`reinstall` 的要重装）。
2. **先看计划（只读）**：`acornfox --json apps set 应用名 名=值 --plan`（平台变量写 `platform.名字=值`，只改这个应用；密码、Key 这类保密的值写成 `名=-`，值从标准输入给一行，不要写在命令里）。让应用跟上现在的值、不改设置：`acornfox --json apps reapply 应用名 --plan`。看输出的 `plan`：
   - `needed` 是 `false`：没有要改的，告诉用户“现在的设置和应用里用的一致”，到此为止。
   - `vars`：哪几项会变，旧值、新值（保密的值只给后 4 位）；`restart`：会不会重启；`env`、`files`、`command`：会改写的环境变量、配置文件、启动命令；`steps`：会在应用里做的步骤；`dependents`：用它提供的服务的应用（它们之后会落在后面）。
3. 把 `plan.summary` 和 `vars` 里的变化用一句话说清：“这会重启 <应用>，大概几秒到一两分钟用不了，数据不动，失败会自动退回原来的设置。”用户这次的话本身就是要改这一项（“改成 X 让它生效”）、而且计划里没有他不知道的后果（`dependents` 不是空的、`vars` 里有他没提的项、`steps` 里有要他新填的东西，都算有），这一句就是计划要点，当已同意，直接做。用户只是问“能不能改”，或计划里有上面这些后果，就再问一句“现在做吗？”。不重启的（`restart` 是 `false`）直接做。
4. 用户同意后运行（会重启的必须加 `--yes`，不加报 `APP-APPLY-05`，什么都没改）：

   ```bash
   acornfox --json apps set 应用名 名=值 --yes
   acornfox --json apps reapply 应用名 --yes
   ```

   命令会等它做完（最多 10 分钟）。输出里 `ok` 是 `true`、`say` 说“已重新生效”才算好；`ok` 是 `false`：`diagnosis.code` 是 `APP-APPLY-03` 的，应用已经退回原来的设置、照常在运行，把 `message` 里的原因告诉用户，改对再试；是 `APP-APPLY-04` 的，**停下**，把原话告诉用户，不要重复运行。
5. 做完用 `acornfox --json apps vars 应用名` 核对：新值在，没有 `APP-VARS-01` 的行；再照 `app-life.md` 的“确认应用能打开”确认它真的能打开。任务 `apps[].affected_apps` 不是空的：这些应用用了它提供的服务，服务的值变了，它们的设置现在落在后面，告诉用户并问要不要也让它们跟上（对每一个重复 2～4 步）。

**平台上的值变了、让所有落后的应用跟上：**

1. `acornfox --json apps affected`：每个应用哪几项和现在的不一样、会不会重启；`--var platform.tz`（或 `uses.需要名.项`、`service:服务名`）看哪些应用用到这个变量，换之前就知道会碰到谁。没有落后的就到此为止。
2. 把名单和会重启的告诉用户，问同意后：`acornfox --json apps reapply --all --yes`（一个一个做，第一个失败就停，不会接着做下一个；先 `--all --plan` 看全部也行）。
3. 改对外方式、域名（`acornfox app set --expose …`、`domain add|remove …`）时，清单用到应用地址的应用会跟着重新生效：命令先算计划，**会重启的要加 `--yes`**（不加会报 `APP-APPLY-05`，访问方式什么都没改），同意了才加；用户只想改访问方式、不想现在重启应用，加 `--no-reapply`，应用里的地址以后用 `apps reapply` 再对。

**必须先停下问用户的：**

- 会重启应用、而用户没有明确要求这一项改动的操作（计划里 `restart` 是 `true`；用户自己说了要改且计划里没有意外后果的，不用再问）；对外开放到公网（照 `app-center.md` 的“对外开放”的规矩另外问）。
- `APP-APPLY-04`（退回也出错）之后的任何动作，包括再运行一次。
- 用户要改的是 `editable: reinstall` 的设置（`APP-APPLY-02`）：要保留数据删掉重装，照“换应用版本、删了再接上旧数据重装”做，先问。

**几种情况：**

- `APP-APPLY-01`：看 `message`。正在装或正在重新生效的，`acornfox install status 任务编号 --wait` 等它结束再来；停着的应用而这次要在应用里做步骤，问用户同意后 `acornfox start 应用名` 再来；清单没存、旧格式、不是从应用中心装的，不能用这个功能，只能删了重装（先问用户）。
- `APP-APPLY-02`：这一项不能改。不要用 `env set` 绕过。
- 值格式不对（`CAT-INST-02`、`CAT-INST-28`）：按 `message` 改，值的要求和安装时一样；`catalog platform-vars` 看哪些平台变量能改、要什么格式。
- 没有变化：`needed` 是 `false`、`changed` 是 `false`，什么都没做；想重启它再做一遍清单里“每次重新生效后的步骤”，加 `--force`（要先问用户，会重启）。
- 配置文件里用户自己改过的内容：清单里写了“只在安装时写”（`overwrite: install`）的文件不会被碰；平台管的配置文件按设置重写。你不要替用户进容器改。

**可以发挥的地方：** 解释每一项设置是干什么的；帮用户判断改哪一项；解释为什么要重启、什么时候做合适（例如没人在用的时候）。

## 查一个应用是用什么设置装的

什么时候用：用户问“这个应用的密码、地址、时区、模型名是怎么设的”，或者排查应用配置（例如怀疑时区、下载源不对）时。只对从应用中心装的应用有用。只读，不改任何东西。它接的服务（例如大模型接口的地址和 Key、邮箱）不在这里：先 `acornfox --json status 应用名` 看 `services` 接的是哪条，再 `acornfox --json services show 服务名` 看那条服务的各项（保密项只显示后 4 位）。v0.5.1 之前没有这个命令（报用法错误，退出码 2），告诉用户要 v0.5.1 起才有，不要自己去翻容器。

**最低路径（照着做）：**

1. 运行。应用名必须写，这个命令不会按当前目录猜（`acornfox --json apps` 看有哪些）：

   ```bash
   acornfox --json apps vars 应用名
   ```

2. 先看三处：
   - `from_catalog` 是 `false`：不是从应用中心装的，没有这些变量。把 `notes` 告诉用户；它的环境变量用 `acornfox env list --app 应用名 --json` 看。到此为止。
   - `manifest.source`：`install`（安装时保存的清单）、`backfill`（升级后补存的）都照常往下看；`manifest.saved` 是 `false` 见下面“清单没存”。
   - `notes`：给人看的说明，转述给用户。
3. 读 `vars`，每个变量一行，按用户问的找对应的行。判断用英文取值，说给用户听用同名的 `*_label`（中文）：

   | 列 | 意思 |
   | --- | --- |
   | `name` | `params.名字` 是这个应用自己的参数；`platform.名字` 是平台按这台机器给的（`platform.tz` 时区、`platform.app.url` 访问地址、`platform.app.scheme` 访问方式 http 或 https、`platform.app.host` 地址里的主机、`platform.mirror.pypi` 和 `platform.mirror.npm` 下载源、`platform.region` 网络区域） |
   | `layer` | 哪一层：`custom` 自定义变量（应用自己的），`system` 平台变量（平台给的） |
   | `class` | 类别：`system` 系统给、`generated` 平台生成、`default` 有默认值、`optional` 可选、`user_required` 必须用户填。空表示清单没存，分不出 |
   | `value` | 安装时保存的值。`masked: true` 表示被遮住了 |
   | `secret` | 是不是密码、密钥、Key 这一类 |
   | `origin` | 值从哪来：`user` 用户填的、`recipe` 配方预填的、`default` 清单默认值、`generated` 平台生成的、`platform` 平台算的、`platform_user` 用户安装时用 `--set platform.名字=值` 改的、`restored` 接上旧数据时恢复的、`install_time` 装时的值（旧版本装的，那时不记是谁给的）、`unset` 没填、`old_data` 沿用旧数据里的（平台不知道，`value` 是空） |
   | `editable` | 清单写的能不能改：`never` 不能改、`always` 随时能改、`reinstall` 重装才能改；空是清单没写（按能改算，平台生成的密码密钥除外）或没存；平台变量里用户能改的是 `per_app`（只改这个应用） |
| `can_edit`、`edit_how` | 现在能不能用 `acornfox apps set` 改这一项；能改的，`edit_how` 是命令（见“改一个应用的设置、让它跟上”） |
   | `used` | 只有平台变量有：这个应用用没用到它。`false` 表示这个值对这个应用不起作用 |
| `value_now` | 只有平台变量有（v0.6.0 起）：按现在的对外方式、域名和这台机器的设置算出来的值。`value` 是装时算好、应用现在用的 |
| `differs`、`code`、`fix` | `differs` 是 `true`、`code` 是 `APP-VARS-01`：装时的值和现在的不一样，应用里用的还是装时的（多半是装完改了对外方式或绑了域名）；`fix` 是怎么办 |

   它需要的服务接了哪条、现在能不能用，不在这张表里：看 `acornfox --json status 应用名` 的 `services`（见 `app-life.md` 的“状态与诊断”）。

4. 只回答用户问的那几项，不用把整张表念一遍。有 `code` 是 `APP-VARS-01` 的行、用户又问到地址（或者问“webhook 地址怎么还是旧的”“时区怎么没跟着换”）时，照这样说：“应用装的时候写进去的 <name> 是 <value>，现在算出来是 <value_now>。应用里用的还是装时的，应用照常能用；要让它用上现在的，需要重启它一下（数据不动）。”用户要换成现在的值：照“改一个应用的设置、让它跟上”做。**不要**用 `acornfox env set` 或进容器去改。密码、密钥、Key 默认只显示后 4 位（`******` 加后 4 位；不到 12 个字符的全遮成 `******`）。说到它们时只说“有值、后 4 位是什么、谁给的”。

**必须先停下问用户的：**

- 看完整的密码和 Key（`--reveal`）：**先问用户**，同意了才运行 `acornfox --json apps vars 应用名 --reveal`。看到的密码和 Key **不要在对话里复述**，也不要写进文件、提交信息或别的命令。用户只是想自己看密码时，优先请他自己在服务器上运行 `acornfox apps vars 应用名 --reveal`，或在 AcornFox 控制台的应用详情里看（v0.6.3 起在“设置”页签的“安装设置”一行里点“显示”，位置见 `access.md` 的“用户问‘在页面上哪里看’”）。
- 用户要改设置：**不要**自己去改容器、进容器改配置文件、改数据卷里的文件，也不要用 `acornfox env set` 绕过：这样改平台不知道，这里显示的值就和实际对不上，以后重装或升级还可能被盖掉。用 `acornfox apps set`，见下一节“改一个应用的设置、让它跟上”（v0.7.0 起；更早的版本没有，`apps set` 报用法错误，照实告诉用户“要升级到 0.7.0 才能改设置”）。应用自己后台里能改的（例如应用的管理员密码）由用户在应用里改；改了以后这里显示的仍是平台保存的值。

**几种情况：**

- 用旧格式的清单装的应用（v0.5.x 时从应用中心装的，`notes` 里写着是旧格式装的；`acornfox --json status 应用名` 的 `legacy_note`、控制台应用详情里也有同样一句说明）：照常运行，能启动、停止、删除，但不接服务（`status` 里没有“它用的服务”，自检也不查它），这一版的新功能（看计划、接服务）用不上。用户要用新功能，只能删掉（保留数据）再从目录装回来，见“换应用版本、删了再接上旧数据重装”：**先问用户**，而且要等目录里这个应用有了新格式的版本（安装时报清单是旧格式，就是还没有，告诉用户，不要反复试）。不急的话不用处理。
- 清单没存（`manifest.saved` 是 `false`，`notes` 里有“清单没存，分不出类别”）：这个应用是 v0.5.1 之前装的，那时不保存清单，升级后本机也找不到它那一版的应用包，所以补不上。应用照常运行，不用处理。这时 `class` 都是空，自定义变量分不出哪些是密码，**一律按密码遮住**（用户名也会被遮住）。照实告诉用户“这个应用装得早，只能列出保存的值，分不出类别”，不要猜。
- `origin` 是 `install_time`：旧版本装的应用，那时不记每个值是谁给的，分不出哪些是用户改过的。照实说“装时的值”，不要说成“默认值”或“用户填的”。
- `from_catalog` 是 `true` 但 `vars` 是空：应用还在安装，等安装任务结束再查。
- `CAT-INST-22`：没有这个应用，`acornfox --json apps` 看名字。
- `CAT-INST-20`：保存的参数解不开。不要自己想办法，把原始输出交给用户。
- 这里显示的是**安装时保存的值**，不是从容器里现读的。用户怀疑应用里实际的值和它不一样时，照实说明这一点。`--json` 里的 `env`（v0.6.0 起）是写进应用的每个环境变量算好以后的值，保密的遮住、只给 `sha256` 指纹，核对用，不念给用户。

## 换应用版本、删了再接上旧数据重装

已装的应用升级到目录里的新版本，用上一节的 `apps upgrade`（先留快照、失败自动退回）。本节是另一件事：用户要删掉应用后又想装回来，或新版本这一版不能原地升级（`APP-UPG-03`）：做法是删掉应用、保留数据，再用原来的安装命令加 `--reuse-data` 装回来。

**最低路径（照着做）：**

1. 删除前先 `acornfox --json status 应用名` 看一眼它现在的状态和 `services`（它接了哪些服务）。和你之前告诉用户的对不上时（例如你说过“卡住”，它其实已经在运行），先把实际情况告诉用户，再问还要不要删。删除要先问用户（会停掉应用）。同意后 `acornfox --json delete 应用名`（**不加** `--volumes`，数据卷保留）。删除被拒、`diagnosis.code` 是 `app_in_use`：别的应用接着它提供的服务，按下面 `app-life.md` 的“生命周期”里那一段做。
2. 只是删了装回原来的版本：跳过这一步。要换新版本的，`acornfox --json catalog sync` 后 `acornfox --json catalog info 应用` 看目录里的版本。
3. 先看计划：`acornfox --json install 应用 --reuse-data --plan`，照 `app-center.md` 的“从应用中心装应用”第 3、4 步处理；再提交：`acornfox --json install 应用 --reuse-data --no-wait`（装的时候用了 `--name` 的，用同一个名字）。只记得应用名、不知道它是目录里哪个应用时，可以只写应用名：`acornfox --json install --name 应用名 --reuse-data --plan`（v0.6.0 起，平台按留下的数据找回它原来是哪个应用）。这样报错、说找不到它原来是哪个应用时，问用户当初装的是目录里哪个应用，写上应用编号再看计划：`acornfox --json install 应用编号 --name 应用名 --reuse-data --plan`。**不用**把以前的 `--set`、`--use` 再写一遍：没写的都按以前的来。用户这次明确要改的才写上。
4. 照 `app-center.md` 的“从应用中心装应用”第 6 步等它装完（`acornfox --json install status TASK_ID --wait`），直到 `done` 是 `true`。没到之前什么结论都不下。
5. 成功后照 `app-center.md` 的“从应用中心装应用”第 7 步发收尾消息；任务 `apps[]` 里下面这几项写在它的 ⑤′（⑥ 的问题之前；没有这几项是服务器版本旧，设置可能没沿用，照实说）：
   - `carried`：沿用了什么，一条一句，照原话转述（例如“沿用以前改过的平台变量：platform.tz=Asia/Tokyo”）。
   - `kept_files`：数据里原有、没有重写的配置文件（用户和应用自己改过的内容都还在）。
   - `file_backups`：因为平台要填的内容变了（`steps` 里“写配置”一步的 `message` 写着变了什么）而重写的配置文件，`backup` 是旧文件另存的名字（在应用的数据卷里）。告诉用户：以前自己改过的内容在这个旧文件里，需要的话照着抄回去；你不要替用户进容器改。
   - 服务和凭据怎么样了**只看 `carried` 和 `must_tell`**：例如“旧的那份没通过检查，已经换了一份”“以前的那份没能收回”这类话原话告诉用户，旧的要不要到提供方应用里删由用户决定。不要自己推断“凭据还是原来那份”或“已经收回了”。
6. 对外方式：不加 `--expose` 时回到这台机器的默认（本节第 3 步计划里的 `apps[].exposure`；没有这一项时是只本机）。本节第 1 步 `status` 里 `exposure` 是 `lan`（以前开放过局域网）、而本节第 3 步看到的计划里是 `local` 的，提交之前问用户要不要照旧开放（问话照 `app-center.md` 的“从应用中心装应用”第 3 步），同意了加 `--expose lan` 再看一次计划，提交时也加上。没在本节第 3 步问过的，收尾消息的 ③ 照常写怎么打开，在 ⑥ 的问题前面加一句“以前开放过局域网，这次回到了只本机”，问题照 ⑥ 问。

沿用的规矩（判断用，不用念给用户）：

| 设置 | 这次没写 | 这次写了 |
| --- | --- | --- |
| 账号密码、平台生成的密钥 | 和以前一样 | 以这次为准 |
| 以前 `--set platform.名字=值` 改过的平台变量 | 恢复以前改的值。v0.5.0 装的应用分不出来，`carried` 里会说“要这次再写一遍”：问用户以前改过哪些，再加 `--set` 重装 | 以这次为准 |
| 需要的服务 | 接回原来那条（它现在能用的话）。别的应用发给它的凭据先核对还能不能接着用，不能用就换一份新的，`must_tell` 里会说；数据库这类（换一份等于接到空库）核对不过不换，安装停下（`CAT-INST-37`，照 `app-center.md` 的“安装出错时”做）；原来那条现在不能用，按计划里的状态处理（第 4 步） | `--use` 以这次为准 |
| 数据里已有的配置文件 | 平台要填的内容没变就不重写；变了（例如接的服务或凭据变了、新版本改了模板）就重写，旧文件先另存为 `文件名.bak-时间`；上一次接旧数据没装好、已经改写过的，这次也重写（旧文件再另存一份） | 同左 |

**可以发挥的地方：** 新版本能不能读旧数据由应用自己决定；用户的数据很重要时，建议先备份再换版本（`app-life.md` 的“备份和恢复应用数据”一节：`acornfox backup create 应用名`）。

## 可以发挥的地方

- 解释新版本改了什么（`plan` 里的设置变化）；建议重要数据先 `backup create` 再升；建议升级放在没人用的时候；告诉用户快照占多大、占的是备份目录的磁盘。
- 解释每一项设置是干什么的、帮用户判断改哪一项、解释为什么要重启、什么时候做合适。
- 新版本能不能读旧数据由应用自己决定；用户的数据很重要时，建议先备份再换版本。

## 必须先问用户的

- 升级本身（会重启）、退回（会丢升级后写进应用的新数据）、补设置的值、调内存、清理磁盘；**用户没有说要升的时候，不要自己加 `--yes`**。
- 会重启应用、而用户没有明确要求这一项改动的操作；`APP-APPLY-04`（重新生效退回时也出错）之后的任何动作；改 `editable: reinstall` 的设置（要保留数据删掉重装）。
- 删除应用（`delete`，不加 `--volumes` 保留数据），接上旧数据重装（`--reuse-data`），对外方式回到默认前问要不要照旧开放。
- 看完整的密码和 Key（`apps vars … --reveal`）：先问，看到的不要在对话里复述。
- 不要用 `acornfox env set` 或进容器去改从应用中心装的应用的设置，平台不知道，显示的值就和实际对不上。
